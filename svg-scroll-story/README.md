# SVG-анимация по скроллу — три этапа

Прототип: `demo.html` (открывать через локальный сервер не обязательно — файл самодостаточный).

Разбор примера [consider.digital/story](https://consider.digital/story/) и механика переходов для трёхэтапной схемы, где объекты на этапах **разные**.

## Как устроен consider.digital/story

Это не морф одной картинки в другую. Это **скролл как playhead таймлайна**, а каждая глава — отдельный sticky-кадр.

### Каркас

Каждая сцена — высокая секция, внутри которой на экране прилипает кадр:

```css
.scene { height: calc(var(--len) * 100vh); } /* 1.5–3.6 экрана */
.stage { position: sticky; top: 0; height: 100vh; }
```

Пока секция едет в документе, картинка стоит. Скролл пересчитывается в прогресс `0…1` этой главы:

```js
p = (pageYOffset - sceneTop) / (sceneHeight - viewportHeight)
```

### Прорисовка линий

Все штрихи — SVG `path` / `line` / `circle` / `rect` без заливки. На старте:

1. `getTotalLength()` → длина контура
2. `stroke-dasharray = length`, `stroke-dashoffset = length` → линия невидима
3. По мере скролла `dashoffset` едет к `0` → линия «рисуется»

Окно прорисовки задано на самом узле: `data-w="0.18 0.3"` значит «рисуй, пока прогресс сцены идёт с 18% до 30%».

Текст и HTML-копирайт появляются так же, только через opacity.

### Что ещё происходит внутри главы

Это уже не dashoffset, а **кастомные функции от того же `p`**:

- лопасти турбин крутятся
- точка бежит по проводу (`getPointAtLength`)
- слои «страницы» разъезжаются как exploded view
- поле точек набирается от центра
- фон `body` плавно меняет цвет
- в конце главы картинка притухает (`data-dim`), чтобы отдать место тексту

### Чего там нет

Сцены **не превращаются друг в друга**. Закончили главу 01 — отлипли — глава 02 рисуется с нуля на новом холсте. Для их сторителлинга этого достаточно: каждая глава — новая метафора.

Для трёхэтапной схемы, где этап должен *стать* следующим, этого мало.

## Почему «просто морф SVG» не подойдёт

Классический morph (GSAP MorphSVG, flubber, SMIL) интерполирует `d` у двух path. Он хорошо выглядит, только если:

- одно и то же число команд
- похожий силуэт
- объект на этапе 2 — «тот же», только чуть другой

Если на этапе 1 дерево, а на этапе 2 завод, морф даст кашу из точек. Значит, нужна другая механика стыка.

## Механика, которую закладывает прототип

Один sticky-холст на все три этапа. Объекты живут в группах и несут **роль**, а не «я должен совпасть контуром с парой».

| Роль | Этап 1 | Этап 2 | Этап 3 |
| --- | --- | --- | --- |
| небо | солнце | фонарь | узел сети |
| вертикаль | дерево | труба | мачта |
| дом | изба | здание | экран |
| человек | идёт | сидит | смотрит |
| extra | холмы | улица / машина | сетка |

Таймлайн скролла одной сцены (~7 экранов):

1. **Прорисовка этапа 1** — как у consider: линии выезжают по `data-w`
2. **Удержание** — кадр стоит, можно повесить мелкий motion (дым, пульс)
3. **Переход 1→2** — handoff по ролям
4. Удержание этапа 2
5. Переход 2→3
6. Удержание этапа 3

### Что такое handoff

Для каждой пары с одной ролью, за прогресс перехода `t = 0…1`:

1. Старый объект **стирается** (dashoffset назад) и слегка **едет** к центру нового.
2. Новый объект **едет с той стороны** и **дорисовывается**.
3. Opacity старого гаснет во второй половине, нового зажигается в первой — чтобы в середине не было дыры и не было двойного наложения.

Пары не обязаны быть похожи. Солнце может стать фонарём: оно «сдаёт место», а не пытается вывернуть контур.

Объекты без пары (`extra` или роль только на одном этапе) стираются / появляются **на месте**, со стаггером.

Порядок ролей чуть сдвинут (небо → вертикаль → дом → человек), чтобы переход читался как очередь, а не как кроссфейд всей картинки.

### Почему так, а не кроссфейд и не частицы

- Кроссфейд двух иллюстраций дешёвый и «презентационный». Не ощущается как превращение схемы.
- Разлёт в частицы красивый, но тяжёлый в производстве и плохо контролируется на телефоне.
- Handoff по ролям работает с **любыми** контурами, читается как смена устройства мира и прямо мапится на вашу таблицу «это становится этим».

Если позже окажется, что какая-то пара *достаточно похожа* (например человек в двух позах), для неё одной можно включить настоящий morph path — движок это переживает. По умолчанию не закладываем.

## Что нужно от иллюстраций

Движок не просит совпадающих контуров. Он просит **сцену как набор именованных групп**.

1. **Три SVG, один артборд.** Один `viewBox` (например 1440×900) на все этапы. Пары стоят в похожих зонах кадра: дерево и труба слева, дом и здание в центре, солнце и фонарь справа. Чем ближе центры пары, тем короче «поездка» и спокойнее переход.
2. **Группы, не плоский файл.** Каждый смысловой объект — `<g id="tree" data-role="tall">…</g>`. Роли можно назвать как удобно, главное — одна таблица соответствий на три этапа.
3. **Обводки, если нужен draw-on.** Эффект «рисунок оживает» требует stroke (и желательно без `fill`). Если иллюстрации заливочные — ставим `data-enter="fade"`: вход/выход будут через прозрачность и лёгкий scale, без прорисовки линии. Оба режима уже заложены.
4. **Чистота экспорта.** По возможности без растров внутри SVG, тяжёлых фильтров, масок и `clipPath` на весь кадр. Трансформы внутри группы нормальны.
5. **Таблица ролей.** В любом виде: «этап1 / этап2 / этап3 / extra?». Если объекту не во что превращаться — он extra: стёрся и всё.

Можно прислать Figma/Illustrator + экспорт SVG. Группы и `data-role` можно разметить уже здесь, если в исходнике объекты хотя бы отдельными слоями.

## Куда это вставлять

`demo.html` — самостоятельная страница, как у consider: один файл, без картинок и библиотек.

Тильда: sticky внутри зеро-блока часто ломается из‑за `overflow: hidden` у родителей. Надёжнее обычный HTML-блок на всю ширину страницы или отдельный экран. Когда иллюстрации встанут, соберём `tilda-embed.html` под конкретный блок.

## Куда править, когда приедут файлы

В `demo.html`:

- группы `#stage-1` / `#stage-2` / `#stage-3` — заменить плейсхолдеры на ваши контуры
- `STAGGER`, `TRAVEL`, объект `P` — тайминг и длина «поездки»
- `ROLES` — список ролей
- копирайт в `.copy` — тексты этапов
